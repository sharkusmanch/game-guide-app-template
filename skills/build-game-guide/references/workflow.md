# Companion workflow

1. Fill the [game brief](game-brief.md) with exact edition, emulator/core and run scope. Pick the release level: manual guide, named save profiles, condition assistance, or optional private integration. Unknown evidence leaves that feature unavailable; it need not block manual guide work.
2. Build a dated source ledger and [evidence matrix](evidence-matrix.md). Record published main/challenge membership and counts independently. An achievement hash/opaque `MemAddr` is not an executable condition. Transient session challenges and actual hardcore awards need their own evidence; save facts cannot recreate them.
3. Generate a new repository from the public template, configure its identity and run its checks. Renaming leaves decoding unsupported. Preserve existing game sources and verified current private-service features when adding an adapter; an older donor checkout is not deployment authority. Keep factual extractor inputs pinned and clean; record revision and dirty status. Test dirty-tree rejection in an isolated copy.
4. Implement the game domain through the [adapter contract](adapter-contract.md). Add only the guide/planner concepts the game needs. Unknown inventory/registration/ownership/history facts remain unknown rather than zero or complete. For real decoding, distinguish constructed/edited/other-core fixtures from genuine target-core captures, and supply independently attributable expected values. Missing target fixtures are explicit skips/open gates, not successful tests.
5. Verify browser/common behavior and game-specific tests; record source, synthetic and target-runtime results separately. A byte digest detects changed bytes, not a stable character/run identity. Mixing history across identities needs explicit assignment. A new browser attempt does not isolate the emulator's save; any gameplay branch uses a player-managed isolated copy, never edits to synced inputs.
6. Fill [review handoff](review-handoff.md) with candidate/base commits, relevant diff, exact commands, private evidence locations and open gates. Obtain the review appropriate to the task and existing authorization; resolve its material findings.
7. Complete [public release](public-release.md) before authorized publication. Start a clean allowlisted publication root if donor history contains private material; `.gitignore` cannot remove reachable history. After CI, verify the real HTTPS Pages project path. Private integration follows its separate [release form](private-release.md), preserving the verified service and testing its small adapter delta.

Example agent invocation after generation/configuration:

> Use $build-game-guide from the installed canonical skill to build Example RPG's manual companion in this generated repository. Read docs/workflow.md and use the bundled forms. Edition: Example RPG, platform/region/revision and core: unknown. Save decoding and hardcore progress remain unavailable until independently supported. Create a sourced manual guide, fill a brief/evidence matrix/review handoff outside public source, and run local checks. Publication and private deployment are out of scope.

The starter README contains generation/configuration/install commands and an ownership map. Its hosting documentation describes the runtime and app-template example; installed skills need no external repository path to resolve these forms.
